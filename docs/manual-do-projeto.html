Capítulo 01

O que este site faz

Antes de qualquer código: qual é o problema que este projeto resolve.

O J&A Cleaning Group é uma empresa de limpeza residencial que atende a Space Coast (Brevard County) e a Treasure Coast (Vero Beach). Este projeto é o sistema completo dessa empresa. Ele tem três públicos, e cada um enxerga uma parte diferente:

QuemOnde entraO que consegue fazer
Cliente / — página pública Ver os serviços e preços, escolher o idioma (inglês, português ou espanhol), e mandar SMS ou ligar para a empresa.
Você (administradora) /admin — área com senha Cadastrar serviços, ler as conversas de SMS, confirmar agendamentos, gerenciar a equipe e ajustar as instruções da assistente virtual.
Equipe /team — área com senha Entrar com a própria conta. As funcionalidades da equipe ainda estão em construção.

A parte mais incomum do sistema: quando um cliente manda SMS para o número da empresa, uma assistente de inteligência artificial responde sozinha — ela sabe os preços, os horários, e se o cliente quiser marcar um serviço, ela cria um pedido pendente na sua agenda para você confirmar depois. O capítulo 10 explica esse fluxo inteiro.

Capítulo 02

Como um site funciona, de verdade

O conceito que precisa vir antes de todos os outros: cliente, servidor e banco.

Quando alguém digita um endereço no navegador, três computadores diferentes entram em ação. Entender essa divisão explica quase todas as decisões deste projeto.

  • O navegador — o computador do visitante Chrome, Safari, o celular da pessoa. Ele não tem nenhum dado da empresa. Ele só sabe pedir páginas e mostrar o que chega. Também é onde cliques, digitação e animações acontecem.
  • O servidor — um computador da Vercel Fica ligado 24 horas por dia na internet. Quando um pedido chega, ele monta a página, consulta o que precisar, e devolve o resultado pronto. É aqui que o seu código roda de verdade.
  • O banco de dados — o MongoDB Atlas Outro computador, em outro lugar, cuja única função é guardar informação de forma permanente. Serviços, clientes, mensagens, agendamentos. Se o servidor desligar e ligar, o banco continua com tudo.
Analogia

Pense num restaurante. O navegador é o cliente sentado à mesa — ele só vê o prato. O servidor é a cozinha: recebe o pedido, prepara e entrega. O banco de dados é a despensa: nada é cozinhado lá, mas sem ela a cozinha não faz nada. O cliente nunca entra na despensa — e é por isso que a senha do banco nunca pode chegar ao navegador.

Este projeto usa o Next.js, que é um framework: uma caixa de ferramentas que cuida da parte chata dessa conversa (rotas, envio, cache) para você escrever só o que é específico da sua empresa.

Capítulo 05

Como nasce uma página

A regra mais importante do Next.js: as pastas são os endereços.

Você não escreve em lugar nenhum "o endereço /admin/services existe". Basta criar a pasta src/app/admin/services/ com um arquivo page.tsx dentro — e o endereço passa a existir. É literalmente isso.

Arquivo na pastaVira o quê
page.tsxA tela que a pessoa vê naquele endereço.
layout.tsxUma moldura em volta: cabeçalho, menu, rodapé. Vale para a pasta e para todas as pastas dentro dela.
route.tsUm endereço que devolve dados em vez de tela. É como outros programas conversam com o seu site.
actions.tsAs funções que salvam coisas (capítulo 07).
[id] (com colchetes)Uma parte variável do endereço. conversations/[id] atende /admin/conversations/qualquer-coisa.

As molduras se empilham

Quando você abre /admin/bookings, o Next.js monta três coisas, uma dentro da outra: 

src/app/layout.tsx            fontes, idioma, o <body> da página
   └─ src/app/admin/layout.tsx   o menu Dashboard · Serviços · Conversas… e o "Sair"
         └─ src/app/admin/bookings/page.tsx   a agenda em si

É por isso que o menu do admin aparece em todas as telas administrativas sem você repetir o código em cada uma. Você escreveu uma vez, em src/app/admin/layout.tsx.

Um componente é uma função que devolve tela

Abra src/app/admin/page.tsx. São 13 linhas. Uma função com um nome, e dentro dela algo que parece HTML. Esse "HTML dentro do código" chama-se JSX, e é assim que o React descreve telas. Trechos entre chaves { } são código de verdade sendo executado no meio da tela — por exemplo {session?.user?.name} coloca o nome de quem está logado ali.

Capítulo 06

Servidor e navegador: quem roda o quê

A distinção que mais confunde no começo — e que aparece o tempo todo neste projeto.

Por padrão, no Next.js moderno, todo componente roda no servidor. Isso é ótimo: ele pode conversar direto com o banco de dados, e o visitante recebe só o resultado pronto, sem nunca ver a senha do banco. 

src/app/page.tsx — roda no servidor
export default async function Home() {
  const services = await listActiveServices();   ← consulta o MongoDB direto
  …
}

Mas algumas coisas só funcionam no navegador: reagir a um clique, lembrar o idioma escolhido, animar algo. Para isso, o arquivo começa com a linha mágica "use client". 

src/components/LandingContent.tsx — roda no navegador
"use client";

const [lang, setLang] = useState("en");   ← lembra o idioma escolhido
Analogia

A cozinha (servidor) prepara o prato. O "use client" é o saleiro que vai junto para a mesa, porque só o cliente sabe quanto sal ele quer. Você manda para a mesa o mínimo necessário — e nunca manda a despensa inteira.

É exatamente esse o desenho da sua página inicial: page.tsx roda no servidor e busca os serviços no banco; depois entrega essa lista pronta para LandingContent.tsx, que roda no navegador e cuida do botão de trocar idioma. Cada um faz o que só ele consegue fazer.

A linha export const revalidate = 60

Está no topo de src/app/page.tsx e quer dizer: "guarde a página pronta e reaproveite por 60 segundos". Sem isso, cada visitante faria uma consulta nova ao banco. Com isso, o site fica mais rápido e mais barato — em troca, uma mudança de preço pode levar até um minuto para aparecer no site público.

Capítulo 07

Formulários que salvam de verdade

Os arquivos actions.ts, e o que significa "use server".

Um formulário na tela precisa, no fim, gravar algo no banco. Mas o formulário está no navegador e o banco só pode ser tocado pelo servidor. A ponte entre os dois são as Server Actions — funções que vivem no servidor e que o formulário pode chamar diretamente.

Veja src/app/admin/services/actions.ts. Toda ação segue quatro passos, sempre nesta ordem:

  • Conferir quem está pedindo requireSession() — se não tem ninguém logado, para tudo. Nunca confie que o botão só apareceu para quem podia clicar.
  • Validar o que chegou parseServiceForm() — nome não pode estar vazio, preço não pode ser negativo, duração precisa ser um número inteiro de minutos.
  • Gravar no banco createService() — a função de src/lib/services.ts que fala com o MongoDB.
  • Atualizar a tela revalidatePath("/admin/services") — avisa o Next.js que aquela página mudou e precisa ser montada de novo. Sem essa linha, você salvaria e a tela continuaria mostrando o valor antigo.

Preços em centavos

Repare que o banco guarda priceCents, não price. Um serviço de US$ 120,00 é gravado como 12000. Isso é padrão em qualquer sistema que lida com dinheiro: números com vírgula têm erros minúsculos de arredondamento no computador, e um centavo perdido por transação vira um problema real. Guarda-se o inteiro e divide-se por 100 só na hora de mostrar — é o que a função formatPrice faz.

Capítulo 08

O banco de dados por dentro

Oito gavetas, e o que cada uma guarda.

O MongoDB organiza a informação em coleções (pense em gavetas de um arquivo) cheias de documentos (as fichas dentro da gaveta). Toda ficha ganha automaticamente um _id: um código único, o "RG" daquele registro.

ColeçãoGuardaCampos principais
servicesOs serviços oferecidosnome, descrição, priceCents, duração, active
customersOs clientestelefone (é ele que identifica a pessoa)
conversationsUma linha de conversa por clientecustomerId, canal, aiEnabled, status
messagesCada mensagem trocadaconversationId, direção (entrou/saiu), quem enviou, texto
bookingsOs agendamentoscustomerId, serviço, data, status, observações
teamMembersAs contas da equipeemail, senha embaralhada, cargo, active
adminsA sua contaemail, senha embaralhada
businessSettingsUma única ficha com os ajustes geraisnome da empresa, horários, instruções da IA

Como as gavetas se conectam

Nenhuma ficha copia os dados da outra. Uma mensagem não guarda o telefone do cliente — ela guarda o _id da conversa, que guarda o _id do cliente, que guarda o telefone. Assim, se o telefone mudar, muda num lugar só. 

customers  ──_id──▶  conversations  ──_id──▶  messages
    │
    └──_id──▶  bookings  ◀──_id──  services

Todo arquivo de lib/ tem a mesma forma

Abra qualquer um — bookings.ts, services.ts, teamMembers.ts — e você vai encontrar sempre o mesmo desenho:

  • uma interface descrevendo o formato da ficha;
  • uma função get…Collection() que abre a gaveta certa;
  • funções de ler (list…, find…);
  • funções de escrever (create…, update…, delete…, set…).

Aprender a ler um desses arquivos é aprender a ler todos os nove.

Por que mongodb.ts é tão estranho

Abrir uma conexão com o banco é lento. Aquele bloco com global._mongoClientPromise existe para abrir a conexão uma vez só e reaproveitá-la — senão, cada vez que você salva um arquivo durante o desenvolvimento, uma conexão nova seria criada, até o banco reclamar de excesso.

Capítulo 09

Login, senhas e permissões

Três arquivos fazem todo o trabalho: auth.ts, proxy.ts e as páginas de login.

Senhas nunca são guardadas

O que vai para o banco é o passwordHash — a senha passada por uma função de embaralhamento chamada bcrypt, que é de mão única. Dá para embaralhar, mas não dá para desembaralhar. Na hora do login, o sistema embaralha o que a pessoa digitou e compara os dois embaralhados. Isso significa que nem você consegue ver a senha de ninguém — e isso é o desejado: se o banco vazar, as senhas continuam protegidas.

Os três cargos

CargoQuem éOnde pode entrar
adminVocê/admin (tudo) e também /team
teamLeadLíder de equipesó /team
helperAjudantesó /team

Em src/auth.ts, a função authorize procura o email primeiro entre os administradores e depois entre os membros da equipe — e devolve o cargo junto. Esse cargo viaja num crachá digital assinado (um token JWT) guardado num cookie do navegador. Assinado quer dizer: ninguém consegue editar o crachá para se promover a admin sem que o servidor perceba.

O porteiro

src/proxy.ts roda antes de qualquer página de /admin ou /team ser montada. Ele lê o crachá e decide:

  • sem login tentando entrar no admin → vai para /admin/login;
  • logado, mas não é admin, tentando o admin → vai para /team/login;
  • já logado e indo para a tela de login → é redirecionado para dentro, já que não precisa entrar de novo.
Importante

O porteiro não é a única proteção. Cada actions.ts confere o login de novo, por conta própria. Isso é intencional: proteção em camadas. Se alguém descobrir como driblar o porteiro, ainda esbarra na segunda tranca.

Como sua conta foi criada

Pelo arquivo scripts/create-admin.ts, rodado uma vez pelo comando npm run create-admin. Não existe tela de "criar conta de administradora" no site — de propósito, para que ninguém possa se cadastrar como dona do sistema pela internet.

Capítulo 10

O robô que responde SMS

A parte mais engenhosa do projeto, do primeiro toque até a resposta chegar.

Um cliente manda "Quanto custa uma faxina completa?" para +1 (321) 252-5141. Ninguém está com o celular na mão. Em poucos segundos ele recebe uma resposta correta, com o preço certo. Isto é o que acontece:

  • Cliente Manda um SMS para o número da empresa.
  • Twilio Recebe a mensagem e imediatamente avisa o seu site, chamando o endereço /api/webhooks/sms. Isso se chama webhook: um aviso automático de um serviço para outro.
  • Seu servidor · conferência Antes de qualquer coisa, validateRequest() confere a assinatura da Twilio. Sem isso, qualquer pessoa na internet poderia fingir ser a Twilio e fazer seu robô responder — às suas custas.
  • Seu servidor · registro Acha ou cria o cliente pelo telefone, acha ou abre a conversa dele, e salva a mensagem recebida no banco.
  • Seu servidor · contexto Monta as instruções da IA (em src/lib/ai.ts): nome da empresa, horário de funcionamento, a lista real de serviços com preços, mais o histórico inteiro daquela conversa.
  • Claude Escreve a resposta — curta, porque é SMS — usando só os preços da lista. A instrução é explícita: nunca inventar preço, e quando não souber, dizer que a administradora vai confirmar.
  • Claude · ferramenta Se o cliente já disse qual serviço quer e quando, a IA aciona a ferramenta propose_booking. Ela não confirma nada: cria um agendamento com status pendente na sua agenda.
  • Twilio O servidor manda a resposta de volta por SMS e guarda uma cópia no banco, marcada como enviada pela IA.
  • Você Abre /admin/conversations e lê tudo o que foi conversado. Em /admin/bookings, os pedidos pendentes esperam você confirmar a data e o horário.

O que é uma "ferramenta" de IA

Um modelo de linguagem só sabe produzir texto. Ele não consegue gravar nada no seu banco. Uma ferramenta resolve isso: você descreve para o modelo uma ação disponível ("propose_booking, que recebe nome do serviço e data preferida"). Quando o modelo decide usá-la, ele devolve um pedido estruturado, e o seu código executa a gravação. O controle continua sendo seu — a IA pede, o seu código decide como fazer.

Detalhe importante

A IA nunca confirma um agendamento sozinha. Ela só cria pedidos pendentes. A confirmação de data e horário é sempre um clique seu em /admin/bookings. Foi uma decisão de desenho, não uma limitação técnica.

Você pode desligar o robô

Cada conversa tem um campo aiEnabled. Se estiver desligado, a mensagem é salva normalmente, mas nenhuma resposta automática sai — útil quando você quiser assumir uma conversa pessoalmente.

Capítulo 11

Senhas, chaves e o arquivo .env.local

O assunto mais importante deste manual, mesmo sendo o mais curto.

O arquivo .env.local, na raiz do projeto, guarda tudo o que é secreto: o endereço e a senha do MongoDB, as chaves da Twilio, a chave da Anthropic, o segredo que assina os crachás de login. Cada linha é NOME=valor, e o código lê esses valores por process.env.NOME.

Esses valores ficam fora do código por dois motivos: para não irem parar no GitHub junto com os arquivos, e para que o mesmo código possa rodar no seu computador e na Vercel apontando para lugares diferentes.

Verificado agora

O .gitignore deste projeto contém a linha .env*, e nenhum arquivo de segredo está no histórico do Git. Está correto.

Cuidado permanente

Nunca cole o conteúdo desse arquivo numa conversa, num chat, numa captura de tela ou numa mensagem. Uma chave da Anthropic exposta pode ser usada por estranhos e cobrada de você; o endereço do MongoDB dá acesso a todos os dados dos seus clientes. Se algum desses valores vazar, o conserto é sempre o mesmo: gerar uma chave nova no site do serviço e substituir a antiga.

Na Vercel, esses mesmos valores são cadastrados no painel do projeto — o .env.local só vale no seu computador.

Rodar no seu computador e publicar

O Node instalado no sistema é a versão 15, antiga demais para este projeto, que precisa da 20 ou maior. Existe um Node 22 instalado à parte, e é por isso que os comandos daqui costumam vir com um prefixo apontando para /opt/homebrew/opt/node@22/bin. Se um comando falhar com uma mensagem sobre versão do Node, é isso.

Glossário

Para consultar quando um termo aparecer e você não lembrar.

Framework
Uma base pronta que já resolve os problemas comuns de um tipo de programa. Aqui, o Next.js.
Biblioteca
Código pronto de outra pessoa que você instala e usa. Ex.: bcrypt, Twilio.
Componente
Um pedaço de tela reaproveitável, escrito como uma função.
JSX
A sintaxe que permite escrever a aparência da tela dentro do código.
Rota
Um endereço do site. Neste projeto, cada pasta em src/app/ é uma.
API
Um endereço que devolve dados, não tela — para outros programas consumirem.
Webhook
Um aviso automático que um serviço externo manda para o seu site quando algo acontece.
Servidor
O computador remoto que monta as páginas e fala com o banco.
Cliente
Neste contexto técnico: o navegador do visitante.
Coleção
Uma "gaveta" do MongoDB. Equivale a uma tabela em outros bancos.
Documento
Uma ficha dentro de uma coleção. Um serviço, um cliente, uma mensagem.
_id
O código único que identifica cada documento.
Hash
Senha embaralhada de forma irreversível. É o que se guarda no lugar da senha.
Sessão
O estado de "esta pessoa está logada", guardado num cookie assinado.
Deploy
Publicar a versão nova do site na internet.
Commit
Uma foto do projeto num momento, salva no histórico do Git.
Variável de ambiente
Um valor configurado fora do código, geralmente secreto. Vive no .env.local.
Tipo
A etiqueta do TypeScript que diz o formato de um dado: texto, número, data.
Server Action
Função que roda no servidor e pode ser chamada por um formulário na tela.
Cache
Guardar um resultado pronto para reaproveitar e não refazer o trabalho.
